# terraform-azure-plane

Terraform module that deploys [Plane](https://plane.so) Commercial on Azure with one `terraform apply`: the network,
an AKS cluster, managed data services, Blob Storage and Plane itself (the `plane-enterprise` Helm chart).

> **Status:** under development, not released. It will be published to the Terraform Registry as
> `makeplane/plane/azurerm` from `v0.1.0`; until then, reference it from this repository. It doesn't change or replace
> the older `azure/terraform` module or the Helm-based guide in `azure/README.md`.

## Requires (not yet released)

This module is built against two plane-enterprise chart changes and a Plane release that are **in progress**. It
can't install a working Plane until they ship:

| Needs | Why | Status |
|---|---|---|
| **Plane with native Azure Blob storage** (api, silo; proxy-only, Workload Identity) | Uploads go to Blob; Plane has no Azure storage backend today (S3 and GCS only) | Being built. `plane_version` default (`v4.0.1`) is a **placeholder** for that release |
| **Plane with Plane AI on Azure Blob** (only with `enable_components.pi`) | Plane AI stores attachments in the same container, through its own proxy routes | Being built with the same Plane PR. The module refuses pi below a floor (`v99.0.0`) that is a **placeholder** until that release is known; preview tags aren't checked |
| **plane-enterprise chart with the Azure Blob values** (`env.storage_provider: AZURE`, `env.azure_storage_account_name`, `env.azure_storage_container_name`, `env.azure_storage_blob_endpoint`, `env.use_storage_proxy: true`) | The module sets these values; the chart has to render them for the api and silo | **Agreed contract**, kept in one block in [`modules/plane/main.tf`](modules/plane/main.tf) ("AZURE BLOB STORAGE") and pinned by `tests/plane.tftest.hcl`. `chart_version` default is a **placeholder** for that release |
| **plane-enterprise chart 3.12.2**: bundled RabbitMQ reading `external_secrets.rabbitmq` | The broker and the apps read one Secret synced from Key Vault (no password in Helm values). Earlier charts refuse this pairing at render time | Being built in parallel |

When they ship: set the real versions as defaults, check the Blob block against the released chart, and run
`terraform test` and `helm template` against the released chart.

## What it creates

| Layer | Resources | Defaults |
|---|---|---|
| Resource group | `<name>-rg`, or an existing empty one (`resource_group`) | Every resource of the deployment lives in it (plus the AKS-managed node resource group) |
| Network | VNet with an AKS node subnet, a subnet delegated to PostgreSQL and a private-endpoints subnet; NAT gateway on a static IP | `10.60.0.0/16`; no subnet has default outbound access, the nodes leave only through the NAT gateway |
| Cluster | AKS with Entra ID + Azure RBAC (local accounts off), Workload Identity, Azure CNI Overlay with Cilium, one node pool with the AKS cluster autoscaler | Kubernetes 1.35, Standard tier (SLA), `Standard_D4ds_v5` (4 vCPU / 16 GB), 2 nodes (range 2–4) over zones 1–3, Azure Linux, patch and node-image auto-upgrades |
| PostgreSQL | Azure Database for PostgreSQL **Flexible Server**, VNet-integrated (no public access) | 15, `GP_Standard_D2ds_v5`, 128 GB auto-grow, zone-redundant HA, TLS required, 14-day backups, delete lock; databases `plane` and `plane_pi` |
| Cache | **Azure Managed Redis** behind a private endpoint | `Balanced_B3` (3 GB), HA, TLS on port 10000, access key (Plane's clients send a password only), an RDB snapshot every 12 hours (`redis.persistence`) |
| Queue | RabbitMQ **in the cluster** (the chart's StatefulSet): Azure has no managed AMQP 0-9-1 | One node, 10 Gi Premium ZRS disk (size set at install, `rabbitmq.volume_size_gb`), credentials from Key Vault |
| Search | OpenSearch **in the cluster** (the chart's StatefulSet), `opensearch.enabled` | On, as on AWS: one node, 50 Gi Premium ZRS disk (size set at install, `opensearch.volume_size_gb`), password from Key Vault |
| Storage | **Azure Blob**: StorageV2 account behind a private endpoint, one container | ZRS, no shared keys (Entra ID only), no public access, versioning (previous versions deleted after 30 days) and 7-day soft delete, delete lock. Plane reaches it with its workload identity (Storage Blob Data Contributor on the container) and serves files through its own proxy: no SAS, no CORS |
| Secrets | Key Vault (RBAC mode, purge protection) holding the database, Redis, RabbitMQ and OpenSearch credentials and the app keys | Generated by Terraform; public endpoint gated by Entra ID RBAC (firewall and private endpoint optional) |
| Edge | **Path A** (`ingress.mode = "automated"`): Traefik on a static public IP (or a fixed private IP), Plane's routes, certificates (Let's Encrypt HTTP-01 or yours from Key Vault). **Path B** (default): none; you bring your ingress | The module configures no DNS: you create the records (`dns_records` output). The addresses are static and known after the first plan |
| Email | Plane's email service (inbound email to work items) on its own static public IP | On by default: ports 25/465/587, sender IP preserved, receiving mail for `intake.<domain>`; you create the A and MX records |
| In cluster (Helm) | External Secrets, Reloader, **plane-enterprise**; path A also Traefik and (with Let's Encrypt) cert-manager | External Secrets and Plane use **Azure Workload Identity**: no client secrets or storage keys anywhere |
| Plane workloads | As on AWS: web, space, admin, api, worker, beat-worker, live, live-exporter, silo, drawio, plus outbox-poller, automation-consumer, runner, agent-consumer, webhook-consumer, iframely, worker-importers, email | api, worker, web and live run 2 replicas spread across nodes, with PodDisruptionBudgets. Plane AI (pi) is off by default (see [Plane AI](#plane-ai)) |

Encryption at rest uses platform-managed keys everywhere in this release; customer-managed keys come later.

## Usage

```hcl
provider "azurerm" {
  features {}
  subscription_id     = "00000000-0000-0000-0000-000000000000"
  storage_use_azuread = true
}

# AKS has local accounts off (Entra ID only): Helm authenticates through kubelogin.
provider "helm" {
  kubernetes = {
    host                   = module.plane.cluster_endpoint
    cluster_ca_certificate = base64decode(module.plane.cluster_certificate_authority_data)
    exec = {
      api_version = "client.authentication.k8s.io/v1beta1"
      command     = "kubelogin"
      args        = ["get-token", "--login", "azurecli", "--server-id", "6dae42f8-4368-4678-94ff-3960e28e3630"]
    }
  }
}

module "plane" {
  source = "git::https://github.com/makeplane/commercial-deployments.git//azure/terraform-azure-plane?ref=<tag>"

  name       = "plane"
  domain     = "plane.example.com"
  location   = "eastus2"
  ingress    = { mode = "automated" } # path A; omit for path B (bring your own ingress)
  acme_email = "ops@example.com"      # Let's Encrypt for the web certificate
}
```

A full example is in [`examples/complete`](examples/complete) (it also sets the Key Vault `features` for a clean
destroy). For a step-by-step installation, see the [deployment guide](docs/deployment-guide.md).

## Prerequisites

- Terraform ≥ 1.10, the **Azure CLI** (logged in) and **kubelogin** (Helm authenticates to AKS with Entra ID).
- **Owner** on the subscription (or resource group), or **Contributor + User Access Administrator**: the module
  creates role assignments (AKS RBAC Cluster Admin, Network Contributor, Key Vault Secrets Officer/User, Storage Blob
  Data Contributor) and delete locks. No Entra ID directory roles are needed (managed identities only).
- Resource providers registered: `Microsoft.ContainerService`, `Microsoft.Network`, `Microsoft.Compute`,
  `Microsoft.DBforPostgreSQL`, `Microsoft.Cache`, `Microsoft.KeyVault`, `Microsoft.ManagedIdentity`, `Microsoft.Storage`.
- A region with 3 availability zones, Azure Managed Redis, zone-redundant PostgreSQL HA and Premium ZRS disks (e.g.
  `eastus2`, `westus3`, `northeurope`, `westeurope`), and quota for the DDSv5 family (24 vCPUs: 4 per node, up to
  4 nodes, plus upgrade surge), 4 PostgreSQL vCores and 3 Standard public IPs.
- Network access from where you run Terraform to the AKS API (public by default; restrict it with
  `api_server_authorized_ip_ranges`) and to the Key Vault.
- An **encrypted remote state backend** (`backend "azurerm"` with `use_azuread_auth`). State holds generated secrets
  (database and RabbitMQ passwords, the Redis key, app keys).
- Azure Policy assignments that deny public IPs, LoadBalancer Services, Redis access keys or Key Vault public access
  break the defaults: check yours first.

## Ingress, certificates and DNS

Two paths, chosen with `ingress.mode`, as on AWS. **The module configures no DNS in either**: after the apply, create
the records from the `dns_records` output.

| | Path A: automated (`ingress.mode = "automated"`) | Path B: bring your own (`ingress.mode = "none"`, default) |
|---|---|---|
| Ingress controller | Traefik behind an Azure load balancer on a static public IP (`ingress.scheme = "internal"`: a fixed private IP in the AKS subnet), installed by the module | Yours, after the apply |
| Plane's routes | Created by the module | Yours: generate them from the chart (as in the AWS module README, "Path B routes") |
| Web certificate | **A.1** Let's Encrypt (`acme_email`, HTTP-01), or **A.2** yours from Key Vault (`ingress.tls_certificate_secret_id`) | Yours |
| Email certificate | Yours from Key Vault (`email.certificate_secret_id`), else self-signed | Same |
| DNS | Yours: A `domain` → `load_balancer_ip`; A and MX for `smtp_domain` | Yours: `domain` → your ingress; A and MX for `smtp_domain` |

**Static addresses:** the module creates the public IPs before the cluster, so `dns_records` is complete after the
first apply (and you can create the records before Plane is up). The Azure load balancer keeps the client IP
(`externalTrafficPolicy: Local`) and its idle timeout is raised to 30 minutes for live's websockets.

**Your own certificates (A.2, and the email certificate):** import each into a Key Vault in the subscription Plane is
deployed to, before the apply (PEM or PFX, with the full chain), and pass the certificate's versionless resource ID
(checked at plan):
`/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.KeyVault/vaults/<vault>/certificates/<name>`. The module
grants External Secrets' identity *Key Vault Secrets User* on that certificate only, adds a SecretStore for that vault
and syncs it into the cluster. The vault must use the RBAC permission model. Renewals in Key Vault are picked up within
an hour.

```bash
az keyvault certificate import --vault-name <vault> --name plane-web --file fullchain-and-key.pem
az keyvault certificate show --vault-name <vault> --name plane-web --query id -o tsv   # versioned URL; use the resource ID form above
```

## Storage (Azure Blob)

Uploads go to a Blob container in a storage account with **no shared keys and no public access**. Plane's pods
authenticate with their workload identity (a user-assigned managed identity federated to the `plane/plane-srv-account`
ServiceAccount) and hold *Storage Blob Data Contributor* on that container only. Browsers never talk to Blob: Plane
runs in **storage-proxy mode** (`use_storage_proxy`, which on Azure can only be `true`; the module, the chart and the
api refuse `false`), so there is no SAS and no CORS, and the account is reached only through its private endpoint. Needs
Plane's Blob support (see "Requires").

**Old versions:** with `storage.versioning_enabled`, a lifecycle policy deletes previous versions 30 days after they
were created (fixed, as on AWS and GCP). Azure counts from when that version was first written, not from when it was
replaced as AWS and GCP do, and soft delete then keeps it for `storage.soft_delete_retention_days`. Creating the
policy is a control-plane call, so the private network and the disabled shared keys don't affect it. Microsoft's
documentation lists no restriction on it running on a private account, but we haven't yet seen it run on one. To turn
versioning off while the delete lock is on, set `deletion_protection = false` in the same apply: the lock also covers
the policy.

### Why uploads go through Plane on Azure (and not on AWS or GCP)

On AWS and GCP, clients upload **directly to storage**: Plane's api returns a signed POST form (a URL plus fields such as
`key`, `policy` and a signature), and the client posts the file as a multipart form, copying every field it was given.
The web app, Space and intake forms, the importers, exports and the email service all upload this way. S3 and GCS
enforce the signed rules themselves, including the exact key, content type, expiry and the allowed size range.

Azure Blob has no equivalent of that form upload:

| What Plane's uploads rely on | S3 / GCS | Azure Blob |
|---|---|---|
| Browser upload with a signed POST form | Yes | No: uploads are an HTTP `PUT` with Azure headers to a SAS URL |
| Size limit enforced by storage from the signature | Yes (`content-length-range`) | No: a SAS can't cap the upload size |
| Signed URLs without account keys | Yes | Yes (user-delegation SAS, which needs an account-level role) |

So on Azure Plane runs in storage-proxy mode: the signed form points at **Plane's api** instead of the storage account.
Clients keep posting the same form; the api checks the signed policy (key, content type, file size, expiry) and writes
the file to Blob over the private endpoint with its workload identity. Downloads go through the api the same way.

**Trade-off:** every upload and download passes through the api pods. Size them for your file traffic, and keep the
ingress body limit at least as large as the upload size limit (path A: `ingress.traefik.maxRequestBodyBytes` in
`plane_values`, 20 MiB by default).

**Plane AI** does the same with its own routes: its signed URLs and mobile upload forms point at Plane AI, which reads
and writes Blob with the same identity. See [Plane AI](#plane-ai).

**Direct uploads on Azure** would be possible later, but they need more than configuration: an Azure `PUT` upload path
in every Plane client, a size check after upload (deleting oversized files), browser access to the storage account
(public network access or an allow-list) with CORS rules, and an account-level role for user-delegation SAS.

## Search (OpenSearch)

On by default, as on AWS. Azure has no managed OpenSearch, so it runs in the cluster from the chart: one node on a
zone-redundant Premium SSD, its password generated into Key Vault. The chart's `plane-api-search-index` Job creates the
indexes after every install and upgrade. `opensearch = { enabled = false }` runs Plane with search indexing off. It is
a single node: back it up with disk snapshots, or re-index from the database (`manage_search_index document index`).

## Plane AI

Off by default. `enable_components = { pi = true }` turns it on, and the module then sets up everything it needs: a
chat model and semantic search, on the same Blob container (through Plane's Workload Identity: no new role on the
storage account) and the `plane_pi` database the module already creates. Plane AI reads its models from its
environment, which the module sets; there is nothing to configure in the admin UI. It needs:

- **`opensearch.enabled`** (the default): at its first start, Plane AI creates the embedding model in the in-cluster
  OpenSearch (an ML connector to the provider), its pipelines and its indexes. With pi on, the module gives OpenSearch
  a 1.5 GB heap in a 3 GiB memory limit.
- **`plane_version`**: the first Plane release whose Plane AI supports Azure Blob storage (named in this module's
  release notes). The module refuses older versions.
- **A chat key and a Cohere key.** Both are required: the module refuses Plane AI without them. Embeddings run on
  Cohere (`pi.api_keys.embedding_model`, default `cohere/embed-v4.0`; or another model below). Chat runs on the
  provider in `pi.api_keys.chat_provider` (below).

**Chat provider.** Any vendor key, or a custom model with its base URL, model and key, turns Plane AI's features on.

| `pi.api_keys.chat_provider` | Chat key in | What Plane AI gets |
|---|---|---|
| `openai` (default) | `OPENAI_API_KEY` | OpenAI's models in the model picker; web search |
| `anthropic` | `CLAUDE_API_KEY` | Anthropic's models; web search |
| `xai` | `XAI_API_KEY` | xAI's models; web search |
| `baseten` | `BASETEN_API_KEY` | The open models Plane AI offers on Baseten; no web search |
| `meta` | `META_API_KEY` | Meta's models (Meta Model API); web search |
| `custom` | `CUSTOM_LLM_API_KEY` | Your own model on any OpenAI-compatible API (pi's custom LLM): exactly that one model, no web search |

With a vendor key, Plane AI calls the vendor's own API, shows its built-in models in the picker, picks the default,
and uses cheaper models of the same vendor for background work. Don't set the `custom` inputs with a vendor: the module
refuses them.

`custom` takes `chat_base_url` and `chat_model` (both required: the API's base URL and the model ID it expects),
`chat_model_name` (shown in Plane AI; default `chat_model`) and `chat_max_tokens` (the model's context window; default
128000, at least 1000). **`custom` requires an OpenAI-compatible API**: the OpenAI Chat Completions API at
`chat_base_url` (for example `https://host/v1`, serving `/chat/completions`), with a bearer key. Azure OpenAI works
through its OpenAI-compatible `/openai/v1` endpoint (`chat_model` is the deployment name), as do vLLM, Ollama, LiteLLM
and OpenRouter. Other APIs, such as Anthropic's native API, don't work with `custom`: use a vendor value, or a gateway
such as LiteLLM in front. With one of OpenAI's newer model IDs (for example a `gpt-6.x` deployment on Azure OpenAI),
Plane AI calls the Responses API instead, so the endpoint must also serve `/responses`; to use OpenAI itself, prefer
`chat_provider = "openai"`.

**Keys.** Before the apply, store the keys in **one Key Vault of yours** in this subscription (RBAC permission model;
the module's own vault doesn't exist yet), and pass each secret's versionless resource ID. A plain-text secret holds
just the key; a JSON secret can hold both, with `chat_key_json_field` and `embedding_key_json_field` naming each field:

```bash
az keyvault secret set --vault-name my-vault --name plane-openai-key --value "$OPENAI_API_KEY"
az keyvault secret set --vault-name my-vault --name plane-cohere-key --value "$COHERE_API_KEY"
```

```hcl
enable_components = { pi = true }
pi = {
  api_keys = {
    chat_key_secret_id      = "/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.KeyVault/vaults/my-vault/secrets/plane-openai-key"
    embedding_key_secret_id = "/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.KeyVault/vaults/my-vault/secrets/plane-cohere-key"
  }
}
```

Or a custom model on Azure OpenAI, with both keys in one JSON secret:

```bash
az keyvault secret set --vault-name my-vault --name plane-ai-keys \
  --value '{"chat_key":"<Azure OpenAI key>","cohere_key":"<Cohere key>"}'
```

```hcl
enable_components = { pi = true }
pi = {
  api_keys = {
    chat_provider            = "custom"
    chat_base_url            = "https://<resource>.openai.azure.com/openai/v1"
    chat_model               = "<deployment name>"
    chat_model_name          = "GPT (Azure OpenAI)"
    chat_key_secret_id       = "/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.KeyVault/vaults/my-vault/secrets/plane-ai-keys"
    chat_key_json_field      = "chat_key"
    embedding_key_secret_id  = "/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.KeyVault/vaults/my-vault/secrets/plane-ai-keys"
    embedding_key_json_field = "cohere_key"
  }
}
```

The module adds a SecretStore for that vault, grants External Secrets' identity *Key Vault Secrets User* on those
secrets only, and copies each key into the env var Plane AI reads (the chat key's, in the table above, and
`COHERE_API_KEY`) in the `plane-ai-providers` Secret, which the chart mounts on Plane AI; the keys never pass through
Terraform or Helm values. Both keys must be in one vault, which can also hold your certificates. If that vault has a
firewall, allow `nat_public_ip`. Terraform needs permission to create role assignments on the vault.

**Embedding model:** one of Plane AI's Cohere models, and its vector dimension:

| `pi.api_keys.embedding_model` | Dimension |
|---|---|
| `cohere/embed-v4.0` (default) | 1536 |
| `cohere/embed-english-v3.0` | 1024 |
| `cohere/embed-english-v2.0` | 4096 |

**Choose the embedding model before the first install**, even if you turn Plane AI on later. Plane's own search
indexes (work items, pages) are created at the first install with the model's dimension, whether Plane AI is on or not
(the module sets `OPENSEARCH_EMBEDDING_DIMENSION` from it). The model is registered in OpenSearch at Plane AI's first
start, and its dimension fixes Plane AI's indexes too. Changing the embedding model afterwards needs Plane's search
indexes and Plane AI's indexes recreated. The chat model changes with an apply.

**Files:** the storage account stays private, so browsers and the mobile app reach files through Plane AI's routes
(`/pi/api/v1/blob/`) on your domain, authorised by a short-lived signature (`PI_INTERNAL_SECRET`, generated by the
module). Every Plane AI file passes through the pi pods, as uploads pass through the api. In path B, your routes must
send `/pi/` to Plane AI and allow request bodies as large as the upload limit.

**Egress:** the pi pods call the chat provider's API, and the OpenSearch pod calls the embedding provider's API, over
the internet through the module's NAT gateway. If you restrict egress, allow HTTPS to the providers you use
(`api.cohere.ai`, and your chat provider's: for example `api.openai.com`, `api.anthropic.com`, `api.x.ai`,
`inference.baseten.co`, `api.meta.ai`, or your custom endpoint).

**Rotating keys:** add a new version of the secret. It's picked up within an hour, and Reloader restarts the pi
workloads. Plane AI puts the embedding key into the OpenSearch connector it creates, so a rotated embedding key also
needs the connector updated.

## Cache (Azure Managed Redis)

`Balanced_B3` by default (3 GB), close to AWS and GCP. `redis.persistence` (default true) saves an RDB snapshot every
12 hours, the longest frequency Azure offers. Azure restores it to the same cache by itself after a failure; the file
can't be downloaded or imported, so it isn't a backup. Azure supports persistence only with high availability, so the
module refuses `persistence` with `high_availability_enabled = false`.

## Email

As on AWS, on by default, receiving mail for **`intake.<domain>`** on ports 25/465/587, with the sender's real IP
(`externalTrafficPolicy: Local`). Azure gives the load balancer a static IP, not a hostname, so create **two records**:
`<smtp_domain> A <email_load_balancer_ip>` and `<smtp_domain> MX 10 <smtp_domain>` (see `dns_records`).
`email = { load_balancer = false }` keeps the service without a load balancer; `email = { enabled = false }` turns it
off. Outbound port 25 from Azure is often blocked; this is inbound only.

## Things to know

- **New installs only in this release**, as on AWS: new app keys and licence identity. Never change `domain`; the
  release and namespace are fixed to `plane`. App keys are generated once and never rotated.
- **In-cluster RabbitMQ and OpenSearch** are single nodes on zone-redundant disks: a zone loss restarts them in another
  zone, but they aren't highly available. Their disks live in the AKS node resource group.
- **RabbitMQ and OpenSearch passwords** are generated once and never regenerated: the servers take them only at first
  boot (their users live on their disks), so a new value in Key Vault alone would lock Plane out. To rotate one:
  1. `terraform apply -replace='module.plane.module.data.random_password.rabbitmq'` (or `.opensearch`): a new value
     in the Key Vault secret `plane-rabbitmq` (or `plane-opensearch`).
  2. Set that value on the server: `rabbitmqctl change_password plane '<new>'` in pod `plane-rabbitmq-wl-0`; for
     OpenSearch, the `admin` and `plane` users through the security plugin's `internalusers` API.
  3. Sync it now instead of within the hour: `kubectl -n plane annotate externalsecret plane-rabbitmq` (or
     `plane-opensearch-creds`) `force-sync=$(date +%s) --overwrite`. Reloader then restarts the apps.
- **Set at install:** `rabbitmq.volume_size_gb`, `opensearch.volume_size_gb` and `persistent_volume_sku` go into the
  StatefulSets' volume claim templates, which Kubernetes can't change: a later change fails the Helm upgrade
  (`StatefulSet ... spec: Forbidden`; set the value back). To grow a disk, snapshot it, leave `volume_size_gb` as it is
  and patch the claim (the module's storage class allows expansion; disks only grow):
  ```bash
  kubectl -n plane patch pvc pvc-plane-opensearch-vol-plane-opensearch-wl-0 \
    -p '{"spec":{"resources":{"requests":{"storage":"100Gi"}}}}'   # RabbitMQ: pvc-plane-rabbitmq-vol-plane-rabbitmq-wl-0
  ```
- **`ingress.scheme` and `zones` are set at install.** Changing the scheme in place removes (or adds) the web public
  IP while Traefik's load balancer is still being moved; changing `zones` replaces every static public IP (web, email,
  NAT) with new addresses. Either can fail with `PublicIPAddressInUse`. To switch the scheme, apply with
  `ingress = { mode = "none" }` (Traefik and the web IP are removed; Plane is unreachable until the next step), then
  with `mode = "automated"` and the new scheme (internal needs your own certificate, A.2), and point your DNS record at
  the new `load_balancer_ip`. If removing the IP fails, the load balancer is still releasing it: wait and apply again.
- **Nodes:** 2 by default, the AKS cluster autoscaler keeps the pool between `node_pool.min_count` and `max_count`.
- **Destroying:** back up first: Flexible Server has no final-backup setting, unlike AWS and GCP (see the
  [deployment guide](docs/deployment-guide.md#11-removing-the-installation)). PostgreSQL and the storage account carry
  delete locks. Set `postgres = { deletion_protection = false }` and `storage = { deletion_protection = false }`, apply,
  then destroy. The locks guard against deletes outside Terraform; a `terraform destroy` plan removes them too.
  Key Vault has purge protection: the destroyed vault stays soft-deleted for `key_vault.soft_delete_retention_days`
  (its name carries a random suffix, so a reinstall doesn't collide). In path B, remove your own load balancers first.
- **Pod and Service ranges** are fixed (`192.168.0.0/16`, `172.16.0.0/16`): `vnet_cidr` and peered networks must not
  overlap them.
