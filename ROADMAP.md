# Plane Terraform modules: roadmap

Use this to decide what goes into the next releases. It assumes **v0.1.0 of the AWS module
(`aws/terraform-aws-plane`) is published**. Each item says what it is, why it's needed and where to start, so it can be
researched and picked up on its own.

## 1. Released: v0.1.0 (AWS, EKS)

`makeplane/plane/aws` on the Terraform Registry: an AWS account to a running Plane Commercial with one
`terraform apply`, on plane-enterprise chart 3.11.3. New installs only.

| Area | In v0.1.0 |
|---|---|
| Infrastructure | VPC (private subnets, NAT), EKS with one managed node group (2 × m7a.xlarge, range 2–4), RDS PostgreSQL 15 Multi-AZ DB cluster, ElastiCache Valkey, Amazon MQ RabbitMQ 3.13, OpenSearch, S3, one customer-managed KMS key, Secrets Manager. Pod Identity throughout, no static keys |
| Secrets | Generated by Terraform into Secrets Manager; External Secrets syncs them into the cluster; Reloader restarts pods on change. The app connects to RDS as the master user |
| Plane | Today's managed-deployment services; search indexes created automatically on install and upgrade |
| Edge | `ingress.mode`: **path A** (`automated`): Traefik behind an NLB with Let's Encrypt HTTP-01, or the customer's certificate from Secrets Manager. **Path B** (`none`, default): the customer brings their own ingress controller and routes. Web NLB can be internal (`ingress.scheme = "internal"`). DNS is always the customer's: the `dns_records` output lists the records |
| Email | Plane's email service for intake email, behind its own internet-facing NLB; certificate from Secrets Manager or self-signed |
| Configuration | One place (`terraform.tfvars`); every input documented with its default |
| Quality | `fmt`, `validate`, tflint, checkov, terraform-docs and `terraform test` (mock providers) in CI; verified end to end on the dev account |
| Docs | Module README, customer deployment guide |

**Known limits of v0.1.0:** the module always creates its own VPC and cluster; no node or pod autoscaling; images
pulled from Docker Hub anonymously; SMTP, SSO and AI keys are set in the admin UI; the EKS API endpoint is public
(`0.0.0.0/0`) by default; one module-managed KMS key; backups are RDS automated backups and a final snapshot only;
the email load balancer is internet-facing; releases are tested by hand.

## 2. Future releases

The next targeted items. Not in priority order; the order and release grouping are decided later.

- **Docker mode.** A second deployment mode for evaluation and small teams: one EC2 instance (Ubuntu, private subnet,
  encrypted EBS data volume) running Plane with `prime-cli setup` and Docker Compose, with Postgres, Redis, RabbitMQ
  and MinIO bundled on the box. Terraform runs setup through SSM Run Command (no SSH, no secrets in user data); the
  instance role reads secrets from Secrets Manager. Plus a Quickstart template.
  - Edge to decide when the work starts: Caddy + Let's Encrypt on an Elastic IP (same on every cloud, cheapest) or
    ALB + ACM (keeps the instance private).
  - Managed data services (RDS, S3) in Docker mode come later: `prime-cli setup` requires S3 access keys, and the
    Compose file falls back to placeholder keys, so keyless S3 from the instance role needs both fixed in prime-cli.
- **GCP module** (`terraform-google-plane`). Same layout, inputs and edge model as AWS: VPC with Cloud NAT, private
  GKE with Workload Identity, Cloud SQL (private IP), Memorystore, GCS (Plane supports GCS natively, keyless), Secret
  Manager. RabbitMQ in-cluster (no managed option on GCP). No DNS records, as on AWS.
- **Release CI with e2e.** On every `v*` tag: assume a role in a sandbox account through GitHub OIDC, apply
  `examples/complete`, smoke-test the URL, destroy, then publish the release. Today releases are tested by hand.
- **Path B route files.** Path B customers render routes themselves with `helm template` (recipe in the README).
  Generate route manifests per chart release in CI for Traefik, NGINX and OpenShift, plus a route table for any
  other controller: path → Service and port, WebSockets on `/live/`, no buffering on streaming paths, 20 MB body
  size, long timeouts, `X-Forwarded-*` handling. The NGINX guide should target a maintained controller
  (ingress-nginx is retired).
- **Least-privilege IAM policy** for the identity that runs Terraform, published as JSON. Today the docs say "in
  practice, an administrator role".
- **Bring your own VPC first, then your own cluster.** Inputs to skip creating the network (`vpc_id`, subnet IDs)
  and later the EKS cluster (`cluster_name`). Needed by customers with an existing landing zone.
- **Node autoscaling.** Cluster Autoscaler on the managed node group's 2–4 range first (the group already has the
  range; nothing scales it); Karpenter or EKS Auto Mode later.
- **Pod autoscaling.** Revive the chart HPA PR helm-charts#133 for api, worker, agent-consumer and webhook-consumer
  (CPU, 2–5 replicas). metrics-server is already installed. Ship it with node autoscaling, or the extra pods only use
  spare capacity.
- **Restricted EKS API endpoint by default.** Today the public endpoint is always on and open to `0.0.0.0/0` unless
  `cluster_endpoint_public_access_cidrs` is set; the private endpoint is always on. Add a toggle to turn the public
  endpoint off, and either require the CIDR list or document running Terraform from inside the VPC (Terraform's Helm
  provider talks to the API directly).
- **`extra_secrets`.** An input map → Secrets Manager → External Secrets → the chart's `*_existingSecret` values, so
  SMTP, SSO, AI and integration keys are managed in Terraform instead of the admin UI.
- **Amazon SES for intake email.** SES receives the intake mail (receipt rule to S3 or SNS) instead of Plane's email
  service and its internet-facing load balancer. Needs Plane to read intake mail from SES; SES email receiving is
  available in only some regions.
- **Image pulls.** Images come from Docker Hub anonymously, so Docker Hub rate limits apply to all nodes through
  the single NAT IP. Optional authenticated pulls first, then an ECR pull-through cache. Also document the outbound
  allow-list (`prime.plane.so`, Docker Hub, `helm.plane.so`, chart repos, Let's Encrypt for path A, AWS APIs).
- **Dedicated database user, or Plane's `RDS_SECRET_ARN` support.** The app connects as the RDS master user, whose
  password RDS rotates; Reloader restarts pods but leaves a short window of failed connections. Either a dedicated
  app user without rotation, or the api's built-in `RDS_SECRET_ARN` support, which handles rotation itself.
- **Version and upgrade policy.** Pin and upgrade EKS, add-ons, the chart and Plane through module releases;
  Renovate on customer templates. Add a pre-upgrade RDS snapshot keyed on the Plane version and a rollback runbook
  (Helm rollback doesn't undo database migrations).
- **AWS Backup plan** as an option, beyond RDS automated backups and the final snapshot.
- **KMS options.** A `kms_key_arn` input (bring your own key) and optional per-service keys. Today one
  module-managed key encrypts RDS, Valkey, S3, Secrets Manager, OpenSearch and EKS secrets.
- **RabbitMQ 4.x.** Amazon MQ runs 3.13; move once Plane is confirmed to work on Amazon MQ RabbitMQ 4.x.
- **Observability option.** The `amazon-cloudwatch-observability` EKS add-on, opt-in. Meanwhile OpenTelemetry can
  be set through `plane_values`.
- **Pinned Elastic IPs** for the web load balancer, as an option (off by default). Makes IPs known at plan time for
  A records and customer allow-lists. Costs 3 Elastic IPs per install (default quota is 5 per region).
- **Sizing data, then size presets.** There's no measured sizing (today's replica counts are defaults). Measure load
  on dev or on Plane's own installation before setting larger defaults. Then presets, e.g. `evaluation` and
  `production` (today's sizes); a small preset needs module changes (single-instance RDS on gp3, single-instance
  RabbitMQ, 1-node OpenSearch), since Multi-AZ DB clusters have no small instance classes.
- **Azure module** (`terraform-azurerm-plane`). Plane has no Azure Blob storage backend (api, silo, pi and the
  chart), so files would need MinIO today. Native Blob support is preferred over an S3-compatible gateway, which
  would need static keys.
- **DNS automation for Route 53 and Cloudflare** (optional, off by default). v0.1.0 writes no DNS: the customer
  creates the records listed in the `dns_records` output (web hostname → load balancer, intake MX and its host).
  Create those records in a Route 53 hosted zone or a Cloudflare zone instead. Points to research:
  - Shape: small submodules (e.g. `modules/dns-route53`, `modules/dns-cloudflare`) the customer calls with the
    `dns_records` output, so the root module doesn't force the Cloudflare provider on everyone.
  - Cloudflare: API token scoped to the zone (from Secrets Manager or the provider's environment variable); records
    must be DNS-only, not proxied, for the intake mail records and the load balancer.
  - Whether to add Let's Encrypt DNS-01 through the same zones, which would allow Let's Encrypt with an internal or
    IP-restricted load balancer (today HTTP-01 needs it internet-facing and open).
- **Migration guide** from today's Kustomize installs and the existing `aws/terraform` module to this module. v0.1.0
  creates new app keys and licence identity, so a migration means backup, apply, restore. The old module and
  `kustomize/` stay until this guide exists.
